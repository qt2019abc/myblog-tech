# sub2api 部署和配置方法

sub2api 适合用于统一管理上游大模型账号、代理出口、分组策略和下游 API Key。对于希望把多个模型账号集中管理、按用途划分访问权限，或者给不同用户分配独立额度的团队来说，这类自托管网关会比直接分散配置更容易维护。

本文结合一次实际部署过程，整理一份基于 Docker Compose 的 sub2api 部署与初始化指南。文中的邮箱、密码、IP、代理名称、出口地址和模型配置均已做脱敏处理，示例仅用于说明方法。

## 一、部署前准备

开始前建议先准备以下内容：

- 一台可运行 Docker 与 Docker Compose 的 Linux 服务器
- 可访问上游模型服务的网络环境
- 一个适合目标业务地区的代理出口
- 管理员邮箱和初始密码
- 计划接入的上游模型账号

如果你的主要用途是给 Codex、OpenAI 兼容客户端或其他 AI 工具提供稳定出口，建议优先确认代理质量是否达标，再导入上游账号。

## 二、使用 Docker Compose 部署 sub2api

官方提供了部署准备脚本，可以直接拉取 `docker-compose.yml` 和环境变量模板，并自动生成一批初始密钥。

```bash
mkdir -p sub2api-deploy
cd sub2api-deploy/
curl -sSL https://raw.githubusercontent.com/Wei-Shaw/sub2api/main/deploy/docker-deploy.sh | bash
```

执行完成后，目录中通常会生成以下内容：

- `docker-compose.yml`：容器编排配置
- `.env`：环境变量文件，包含自动生成的随机密钥
- `.env.example`：示例配置
- `data/`：应用运行数据目录
- `postgres_data/`：PostgreSQL 数据目录
- `redis_data/`：Redis 数据目录

部署脚本会自动生成类似下面这些敏感配置：

- `POSTGRES_PASSWORD`
- `JWT_SECRET`
- `TOTP_ENCRYPTION_KEY`

这些值应视为生产凭证，务必妥善保管，不要提交到代码仓库，也不要直接发到聊天群或工单系统中。

## 三、修改基础配置

在首次启动前，建议先编辑 `.env` 文件，补齐管理员登录信息。例如：

```dotenv
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=<your-strong-password>
```

这里有几个建议：

- 不要使用默认弱口令
- 管理员邮箱建议使用专门的运维邮箱
- 如部署在公网，建议同时配合反向代理、访问控制或仅内网开放

如果其余配置没有特殊要求，可以先保持脚本生成的默认值，等服务跑通后再逐项调整。

## 四、启动服务并访问管理界面

完成 `.env` 配置后，启动服务：

```bash
docker-compose up -d
```

查看运行状态：

```bash
docker-compose ps
docker-compose logs -f sub2api
```

默认情况下，Web 管理界面可通过以下地址访问：

```text
http://<服务器IP>:8080
```

如果是首次启动且未手动指定管理员密码，系统有些场景下会在日志中输出自动生成的密码。因此遇到无法登录时，第一步就是查看容器日志确认初始化信息。

## 五、管理员初始化配置

sub2api 部署完成后，真正影响可用性的不是“服务是否启动”，而是管理端的几项基础配置是否合理。实践中最关键的通常是代理、分组、上游账号和下游用户这四部分。

### 1. 配置代理出口

进入管理页面后，优先在 IP 管理中配置代理。不同模型或客户端对出口地区较为敏感，建议按实际用途选择合适地区。

例如：

- 面向 Codex 或需要美国出口的模型访问，优先配置美国地区代理
- 配置完成后执行连接测试和质量检查
- 只有测试通过后，再把该代理绑定到正式业务分组

一个健康代理通常应满足以下条件：

- 连接测试通过
- 质量检查通过率高
- 无明显告警
- 出口地区符合上游服务要求

文中的实际代理名称、出口 IP 和评分结果已脱敏，原则上只需要关注“能否稳定通过测试”和“地区是否匹配业务需求”。

### 2. 创建分组

建议在分组管理中按用途创建不同分组，而不是让所有请求共用一个默认池。常见分组思路如下：

- `codex-us`：给 Codex 或需要美国出口的工具使用
- `chat-general`：通用聊天场景
- `high-cost-models`：高成本模型单独隔离
- `testing`：测试环境专用

这样做的好处是：

- 可以把不同代理、模型和账号绑定到不同用途
- 便于后续做额度控制和故障隔离
- 下游用户创建 Key 时更容易选对资源池

### 3. 添加上游账号

在账户管理页面中添加上游模型账号。这里的关键不是“先加多少账号”，而是“每个账号归属哪个分组”。

建议至少确认以下几点：

- 上游账号可正常调用
- 账号绑定了正确的分组
- 代理出口与账号用途匹配
- 预估额度足够覆盖目标业务

如果后续发现某个客户端调用异常，先检查它所选分组，再检查该分组下是否确实绑定了可用上游账号。

### 4. 创建下游用户并充值

在用户管理中创建下游子账户后，不要忽略“充值”这一步。很多调用失败并不是模型或代理有问题，而是用户余额不足。

一个典型报错如下：

```json
{"code":"INSUFFICIENT_BALANCE","message":"Insufficient account balance"}
```

当看到这类 `403` 错误时，优先排查：

- 子账户是否已创建
- 管理员是否已给该用户充值
- 用户选择的分组是否有可用上游账号

### 5. 子账户创建自己的 API Key

子账户登录后，可以创建自己的 API Key，并选择管理员分配的分组。后续客户端接入时，通常只需要：

- Base URL：sub2api 服务地址
- API Key：子账户生成的 Key
- Model：该分组支持的模型名

这样既能实现统一代理出口，也能把不同用户的调用量、余额和用途分开管理。

## 六、客户端接入示例

以 Codex 类纯 API 客户端为例，可以参考以下接入方式：

- Base URL：`http://<服务器IP>:8080`
- Key：填写子账户生成的 API Key
- 接入方式：选择纯 API 模式
- 模型：填写管理员允许使用的模型名称
- 上游协议：选择 `Response API`

如果客户端带有“测试模型”或“连通性测试”选项，建议填与正式调用一致的模型名，避免出现“测试配置和实际配置不一致”的情况。

需要特别注意两点：

- 模型名要以 sub2api 当前实际支持和映射后的名称为准
- 如果客户端测试失败，优先检查模型名是否拼写错误

例如把 `gpt` 写成 `gtp`，就是非常常见但不容易第一眼发现的错误。

## 七、常见问题排查

### 1. 管理页面能打开，但调用一直失败

优先检查顺序建议如下：

1. 子账户是否有余额
2. 子账户选择的分组是否正确
3. 分组下是否绑定了可用上游账号
4. 当前代理是否通过连通性和质量测试
5. 模型名是否正确

### 2. 某些客户端可用，某些客户端不可用

这类问题通常与以下因素有关：

- 不同客户端使用的上游协议不同
- 客户端填写的 Base URL 不一致
- 客户端测试模型与实际调用模型不一致
- 某个客户端对出口地区更敏感

建议先用最简单的方式验证：

- 选一个已知可用的分组
- 选一个已知可用的模型
- 使用同一把 Key 做最小化测试

### 3. 代理测试通过，但实际调用仍不稳定

这通常说明“能连上”不等于“长期稳定可用”。可以从以下角度继续排查：

- 代理出口是否频繁变化
- 高峰时段延迟是否显著升高
- 上游服务是否对该地区出口更严格
- 某个分组下是否混入了质量不一致的代理

如果业务场景对稳定性要求高，建议将测试代理和生产代理分组隔离。

## 八、运维建议

为了让 sub2api 更适合长期运行，建议补充以下运维措施：

- 定期备份 `.env` 与数据目录
- 通过反向代理增加 HTTPS 和访问控制
- 为不同业务创建独立分组，避免资源混用
- 定期检查上游账号余额、有效期和调用成功率
- 变更代理后及时重新做连通性和质量检查
- 记录每个客户端使用的协议、模型名和分组，减少排障成本

## 九、总结

sub2api 的部署并不复杂，使用 Docker Compose 基本可以快速启动。真正决定体验的是后续的管理配置是否清晰，尤其是代理出口、分组设计、上游账号绑定和下游用户额度管理。

如果只完成“容器启动”而没有把这些基础配置梳理好，后续很容易出现模型不可用、分组选错、余额不足或客户端测试失败等问题。比较稳妥的做法是先跑通一个最小可用链路，再逐步扩展到多个分组、多个上游账号和多个下游用户。
