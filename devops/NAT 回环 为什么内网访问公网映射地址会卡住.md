
## 引言

在一种常见的内网部署中，Web 服务运行在局域网服务器上，出口路由器或防火墙通过端口映射将服务开放到公网：

```text
外网用户
    |
    | 访问 http://203.0.113.10:8765
    v
公网路由器/防火墙
    | DNAT：203.0.113.10:8765 -> 192.168.10.20:8765
    v
Nginx 0.0.0.0:8765
    | 反向代理
    v
Web 应用 127.0.0.1:8766
```

其中：

- `203.0.113.10` 是本文使用的示例公网地址；
- `192.168.10.20` 是内网服务器地址；
- Nginx 对外监听 `8765`，应用只监听本机 `127.0.0.1:8766`；
- 出口设备把公网 `8765` 端口映射到服务器的 `8765` 端口。

外网访问完全正常，内网通过 `http://192.168.10.20:8765` 访问也正常，但内网用户访问 `http://203.0.113.10:8765` 时，可能出现页面能打开、提交接口卡住，或者浏览器报告 `ERR_CONNECTION_RESET`。这类问题通常不是应用逻辑故障，而是出口设备不支持或没有正确配置 NAT 回环。

## 什么是 NAT 回环

NAT 回环也称 NAT Loopback、Hairpin NAT 或 NAT Reflection。它允许局域网内的客户端通过出口设备的公网地址，访问同一局域网内经过端口映射发布的服务。

一次正常的外网访问只需要处理从 WAN 到 LAN 的流量：

```text
外网客户端 198.51.100.25:53000
        -> 203.0.113.10:8765
        -> DNAT
        -> 192.168.10.20:8765
```

服务器返回数据时，出口设备根据连接跟踪状态执行反向转换：

```text
192.168.10.20:8765
        -> 198.51.100.25:53000
        -> 反向 NAT
        -> 响应源地址表现为 203.0.113.10:8765
```

客户端发出的请求和收到的响应经过同一台 NAT 设备，路径对称，因此 TCP 连接可以正常建立和维持。

NAT 回环的特殊之处在于，请求从 LAN 进入出口设备，转换后又从 LAN 发回，因此流量看起来像在出口设备上“折返”了一次。

## 内网访问公网地址时发生了什么

假设内网客户端地址为 `192.168.10.50`，它访问 `203.0.113.10:8765`。一个完整的 NAT 回环通常需要同时执行 DNAT 和 SNAT。

### 第一步：DNAT 转换目标地址

出口设备识别到公网地址和端口对应一条映射规则，将目标地址改为内网服务器：

```text
转换前：192.168.10.50:53000 -> 203.0.113.10:8765
转换后：192.168.10.50:53000 -> 192.168.10.20:8765
```

### 第二步：SNAT 转换源地址

由于客户端和服务器位于同一子网，出口设备还需要把源地址转换为自己的内网地址，例如 `192.168.10.1`：

```text
DNAT 后：192.168.10.50:53000 -> 192.168.10.20:8765
SNAT 后：192.168.10.1:61000  -> 192.168.10.20:8765
```

这样，服务器会把响应先发送给出口设备，再由出口设备恢复连接两端原本看到的地址：

```text
192.168.10.20:8765 -> 192.168.10.1:61000
        -> 反向 NAT
203.0.113.10:8765  -> 192.168.10.50:53000
```

客户端始终认为自己在与 `203.0.113.10:8765` 通信，TCP 四元组保持一致，连接可以正常完成。

## 为什么只做 DNAT 仍然可能失败

如果出口设备只执行 DNAT，没有对源地址执行 SNAT，服务器看到的源地址仍是 `192.168.10.50`。因为服务器与客户端处于同一子网，服务器会绕过出口设备，直接把响应发送给客户端：

```text
请求路径：
192.168.10.50 -> 出口设备 -> 192.168.10.20

响应路径：
192.168.10.20 ----------------> 192.168.10.50
                 直接返回
```

这形成了非对称路径。客户端发起连接时，目标是 `203.0.113.10:8765`，收到的数据却可能直接来自 `192.168.10.20:8765`。该响应与客户端正在等待的 TCP 连接不匹配，会被协议栈丢弃或触发连接重置。

另一种情况是出口设备根本不对 LAN 侧访问自身公网地址的流量应用端口映射规则。请求可能被当作访问设备自身，也可能被防火墙直接丢弃。此时连接通常会超时或立即被重置。

因此，NAT 回环不是“配置了公网端口映射就自然具备”的能力。设备需要支持 LAN 到 LAN 的 DNAT、配套 SNAT 以及正确的连接跟踪。

## 为什么页面能打开，提交接口却失败

页面能打开并不能排除 NAT 回环问题。常见原因包括：

1. 浏览器缓存了 HTML、JavaScript 或 CSS，部分静态资源并未重新经过故障链路。
2. 静态请求体积小、耗时短，而接口请求持续时间更长，更容易触发出口设备的连接跟踪、超时或状态转换缺陷。
3. 页面加载与接口提交使用了不同的 TCP 连接。前一个连接偶然成功，不代表后续连接也能正确回环。
4. 出口设备对不同连接状态、报文大小或会话持续时间的处理不一致。
5. 后端完成处理并写入响应后，响应仍可能在 NAT 返回路径上被丢弃或重置。

最后一点尤其容易造成误判。假设 Nginx 和应用日志均出现：

```text
POST /api/generate HTTP/1.1 200
```

这只能证明请求到达了服务器，并且服务器生成了 HTTP 200 响应；不能证明响应已经完整到达浏览器。浏览器同时报告下面的错误并不矛盾：

```text
POST http://203.0.113.10:8765/api/generate net::ERR_CONNECTION_RESET
TypeError: Failed to fetch
```

应用层日志观察的是服务器一侧，浏览器错误反映的是客户端一侧。两者之间还存在 Nginx、服务器网络栈、交换网络、出口设备 NAT 状态表和客户端网络栈。任何一段返回路径出现问题，都可能形成“服务端 200，客户端无响应”的现象。

## 用对照实验定位问题

排查时不要只反复刷新页面。最有效的方法是从不同网络位置访问同一个服务，形成对照。

| 测试位置 | 访问地址 | 结果 | 说明 |
| --- | --- | --- | --- |
| 内网客户端 | `http://192.168.10.20:8765` | 正常 | 应用、Nginx 和内网链路基本正常 |
| 外部网络，例如手机热点 | `http://203.0.113.10:8765` | 正常 | 公网端口映射和 WAN 到 LAN 路径正常 |
| 内网客户端 | `http://203.0.113.10:8765` | 失败 | 高度指向 NAT 回环或内网 DNS 问题 |

如果第三组测试失败，而前两组正常，应用本身通常不是首要排查对象。

### 检查监听状态

在服务器上确认 Nginx 和应用各自监听正确的地址：

```bash
ss -lntp | grep -E ':8765|:8766'
```

期望看到：

```text
Nginx    监听 0.0.0.0:8765
Web 应用 监听 127.0.0.1:8766
```

应用只绑定环回地址可以避免它绕过 Nginx 直接暴露到网络。

### 分层验证服务

先验证应用，再验证本机 Nginx：

```bash
curl -i http://127.0.0.1:8766/login
curl -i http://127.0.0.1:8765/login
```

然后分别在内网客户端和真实外部网络测试内网地址、公网地址。测试公网路径时，应使用手机热点等真正位于局域网之外的网络，不能把“内网访问公网地址”当作外网测试。

### 同时观察两层日志

```bash
journalctl -u web-service -f
tail -f /var/log/nginx/access.log /var/log/nginx/error.log
```

若接口失败时两层日志都记录了 `200`，排查重点应从应用处理逻辑转向响应返回路径、NAT 状态和出口设备日志。

必要时可以抓包确认流量是否对称：

```bash
sudo tcpdump -ni any 'tcp port 8765 or tcp port 8766'
```

重点观察：

- 请求的源地址是内网客户端，还是经过 SNAT 后的网关地址；
- 响应是否返回给网关；
- 是否出现 TCP `RST`；
- 同一连接的请求和响应是否经过同一路径。

## 解决方案

### 方案一：内外网 DNS 分流

这是最推荐的长期方案。为服务配置统一域名，例如：

```text
service.example.com
```

公网 DNS 返回公网地址：

```text
service.example.com -> 203.0.113.10
```

内网 DNS 返回服务器内网地址：

```text
service.example.com -> 192.168.10.20
```

这种方式也称 Split-Horizon DNS 或 Split DNS。内外网用户使用同一个 URL，但内网流量不会绕到出口设备的公网地址，因此不依赖 NAT 回环能力。

使用域名还有一个重要好处：后续配置 HTTPS 时，内外网可以继续使用同一证书和同一站点地址，不需要让用户记忆两套 IP。

### 方案二：内网直接使用内网地址

这是最快的临时处理方式：

```text
内网用户：http://192.168.10.20:8765
外网用户：http://203.0.113.10:8765
```

它不需要修改出口设备，但用户需要区分当前所处网络。若页面使用 Cookie 登录，用户在内外网地址之间切换时还可能需要重新登录，因为 Cookie 按域名或主机隔离。

### 方案三：在出口设备上启用 NAT 回环

如果路由器或防火墙支持 Hairpin NAT，可以启用相应功能。其逻辑通常包括：

```text
1. LAN 客户端访问公网 IP 时执行 DNAT
2. 将目标改为内网服务器
3. 对源地址执行 SNAT 或 Masquerade
4. 使用连接跟踪完成双向反向转换
```

不同厂商可能将该功能命名为 NAT Loopback、NAT Reflection、Hairpin NAT、回流 NAT 或 U-Turn NAT。具体配置应以设备文档为准。

需要注意，启用 NAT 回环后，服务器日志中的客户端地址可能变成网关地址。若业务需要记录真实客户端 IP，内网 DNS 分流通常比在四层做回环 NAT 更清晰。

### 方案四：使用统一入口或专用接入方式

对于安全要求更高的系统，可以让外部用户通过 VPN、零信任接入平台或独立边界反向代理访问服务。这样可以减少直接暴露端口，并统一身份认证、TLS、访问控制和审计。

## Nginx 在这个问题中的作用边界

Nginx 反向代理配置可能如下：

```nginx
server {
    listen 8765;
    server_name service.example.com;

    location / {
        proxy_pass http://127.0.0.1:8766;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_connect_timeout 10s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;
        client_max_body_size 20m;
    }
}
```

这类配置能够改善上游连接管理、超时控制和日志记录，但不能修复出口设备上的 NAT 回环。Nginx 收到请求之后才有机会工作；如果响应在出口设备的回流路径上被错误处理，调整 `proxy_read_timeout` 通常没有作用。

同样，后端从 `0.0.0.0` 改为 `127.0.0.1` 是合理的安全收敛，但它解决的是应用暴露范围问题，不是 NAT 回环问题。排查时应明确每一层配置的职责，避免把网络层故障归因于应用或反向代理。

## 常见误区

### “端口映射能被外网访问，内网访问公网地址也一定能用”

不一定。普通端口映射验证的是 WAN 到 LAN 的 DNAT；NAT 回环要求设备额外处理 LAN 到 LAN 的折返流量和源地址转换。

### “后端日志是 200，所以浏览器一定收到成功响应”

不一定。日志中的 200 只代表服务端完成了响应处理，无法证明响应穿过全部网络设备并到达客户端。

### “把 Nginx 超时调大就能解决”

只有上游处理确实超时时才有效。若浏览器报告连接重置，且服务器已经返回 200，应优先检查 NAT、连接跟踪和返回路径。

### “在服务器 hosts 文件里绑定域名可以解决所有客户端的问题”

服务器自身的 `hosts` 只影响服务器解析。要让内网用户绕过公网地址，需要修改每台客户端的解析，或者更合理地在内网 DNS 上配置分流记录。

## 排查结论模板

遇到类似问题时，可以用下面的逻辑快速收敛：

```text
内网地址访问正常
    +
真实外网访问公网地址正常
    +
内网访问公网地址失败
    +
服务端能看到请求，甚至记录 200
    =
优先检查 NAT 回环、SNAT 和非对称返回路径
```

推荐的处理优先级是：

1. 使用统一域名并配置内外网 DNS 分流；
2. 暂时让内网用户访问内网地址；
3. 确有需要时，在出口设备上正确配置 Hairpin NAT；
4. 对高安全场景采用 VPN、零信任接入或边界代理。

## 总结

NAT 回环问题的核心不是“请求能不能到达服务器”，而是一次 TCP 会话的请求和响应能否经过一致、可追踪的地址转换路径。

当内网客户端通过公网映射地址访问同一内网服务时，出口设备通常必须同时完成 DNAT、SNAT 和连接跟踪。缺少其中任何一环，都可能导致非对称路由、响应丢弃或连接重置。服务端记录 HTTP 200 与浏览器报错可以同时成立，因为它们观察的是网络链路的不同端点。

在企业内网中，使用统一域名配合内外网 DNS 分流，通常比依赖 NAT 回环更简单、更稳定，也更适合后续接入 HTTPS 和统一运维。
